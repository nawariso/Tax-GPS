# Tax GPS — รีวิวผลิตภัณฑ์, requirement และความถูกต้องของ domain

วันที่รีวิว: 15 ตุลาคม 2026 (Asia/Bangkok)

ฐานโค้ด: `de85aee` บน repo ปัจจุบัน ตรวจ README, requirement P1-001/003/004,
domain engines, policy/catalog, local demo, tests และภาพหน้าจอ Stage 3 ที่มีอยู่
ประกอบการตรวจ source และ frontend lifecycle tests ไม่ใช่การตรวจ browser สดครบทุกหน้า

เอกสารนี้เป็นผลรีวิวและข้อเสนอปรับ requirement ไม่ได้เปลี่ยนสถานะ acceptance ของ
milestone เดิม และไม่ใช่การรับรองกฎหมายทุกข้อใน policy pack
สคริปต์ประกอบใช้ข้อมูลสมมุติทั้งหมด ไม่มีการอ่านโปรไฟล์ส่วนตัว

## ข้อสรุปที่ควรใช้ตัดสินใจ

แนวคิดเหมาะกับการเป็นเครื่องมือวางแผนภาษีและการใช้เงิน โดยตอบสามคำถามตามลำดับ:

1. ปีนี้ภาระภาษีทั้งปีประมาณเท่าไร และยังต้องจ่ายเพิ่มหรือคาดว่าจะได้คืนเท่าไร?
2. มีสิทธิจากสิ่งที่จ่ายไปแล้วซึ่งยังไม่ได้รวมในฐานภาษีหรือไม่?
3. สำหรับเงินก้อนใหม่ ทางเลือกต่าง ๆ แลกภาษี สภาพคล่อง ความเสี่ยง และมูลค่าอนาคตอย่างไร?

ปัจจุบัน repo ทำแกนคำนวณและเงื่อนไขได้ละเอียด แต่ฐานภาษีรองรับโปรไฟล์แคบ และยัง
ตอบข้อ 3 ได้เพียงผลภาษี/เงินสดของ Thai ESG เทียบกับไม่ใช้เงินเพิ่ม
ผมเสนอให้ปิดช่องว่างฐานภาษี แล้วเพิ่มการทดลองจำนวนเงินและการเปรียบเทียบที่ใช้งบเดียวกัน
ก่อนเพิ่ม optimizer หรือขยาย persistence เป็นระบบใหญ่

## สิ่งที่ควรรักษาไว้

- ใช้ Decimal/Money, PIT ขั้นบันได และผลต่าง PIT จริงเมื่อข้ามฐานภาษี
- แยก tax, discovery, financial guardrails และ candidates ชัดเจน
- เวอร์ชัน policy และ replay ทำให้ตรวจผลเดิมได้โดยไม่พึ่ง AI หรือ clock แฝง
- มี NO_ACTION, รักษาเงินสำรอง และไม่บวกเงินคืนภาษีสมมุติเข้าสภาพคล่องทันที
- Solar/artwork ที่กฎไม่พร้อมยังไม่ถูกเปิดใช้ ลดโอกาสนำข่าวมาใช้เป็นสิทธิภาษี
- UI ยกเลิกผลเก่าเมื่อ input เปลี่ยน และป้องกัน response เก่ามาทับผลใหม่
- แยก product policy เช่นเงินสำรอง 3 เดือน/เกณฑ์หนี้ 15% ออกจากกฎหมาย

## ข้อค้นพบเรียงตามความสำคัญ

P1 ในตารางหมายถึงต้องปิดก่อนใช้ผลกับโปรไฟล์จริงที่เกี่ยวข้อง
P2 หมายถึงข้อกำหนดหรือคุณภาพที่ควรปรับก่อนขยายผลิตภัณฑ์
ระดับนี้เป็นผลรีวิว ไม่ใช่ severity enum ที่แอปมีอยู่

| ID | ระดับ | ข้อค้นพบ | ผลกระทบและข้อเสนอ |
| --- | --- | --- | --- |
| F01 | P1 | core รับ retirement contributions แต่คืน `READY` โดยยังไม่หักจาก taxable income | tax baseline และผลประหยัดเพิ่มผิดสำหรับโปรไฟล์ที่มีรายการลดหย่อนเกษียณจริง; ต้องรองรับเป็นรายประเภท หรือคืนสถานะไม่รองรับจาก core |
| F02 | P1 | Thai ESG/ESGX shared usage ลด capacity แต่ไม่ลด baseline PIT | เป็นข้อจำกัดที่เอกสารประกาศไว้ แต่ input ชื่อ “ใช้ไปแล้ว” เสี่ยงถูกใช้เป็นโปรไฟล์จริง; ต้องแยกธุรกรรม/ยอดที่ลดหย่อนได้จริงออกจาก capacity fact |
| F03 | P1 | `Parent.eligible=None` ถูกคำนวณเป็นไม่หักสิทธิ แต่ tax state ยัง `READY` | discovery บอกต้องการ input ส่วน tax core ดูเหมือนผลพร้อมใช้; ต้องมีสถานะผลบางส่วนหรือไม่พร้อมที่ consumer ทุกตัวเห็นตรงกัน |
| F04 | P1 | source ของ Thai ESG ใน catalog มี title/date ไม่ตรงกับ URL และ URL ไม่อธิบาย shared pool ปี 2026 | metadata และ hash ที่ครบไม่พิสูจน์สาระกฎหมาย; เปลี่ยน evidence ผ่านการออก catalog version ใหม่และ review |
| F05 | P1 สำหรับ full-profile MVP | ยังไม่มีช่องกรอกสิทธิพนักงานที่พบบ่อย เช่นประกันชีวิต/สุขภาพ และสถานะคู่สมรส | แอปไม่สามารถตรวจได้ว่ามีรายการนอกขอบเขตเหล่านี้ตกหล่น; ต้องถาม coverage หรือรับรายการจริงก่อนเรียกผลว่า baseline ครบ |
| F06 | P2 / product gap | ไม่มี withholding reconciliation และ annual forecast ที่แยกยอดจริงกับคาดการณ์ | “ภาษีทั้งปี” และ “เงินที่ต้องจ่ายเพิ่ม” เป็นคนละตัวเลข; ผู้ใช้ต้องเห็นทั้งคู่พร้อมสถานะข้อมูล |
| F07 | P2 / scope limitation | production candidate มีทางใช้เงินที่เปิดอยู่เพียง Thai ESG และสร้างหลัก ๆ เป็น 0/เพดาน | ยังไม่มีคู่เปรียบเทียบ RMF, ลงทุนทั่วไป, โปะหนี้ หรือจำนวนเงินกลางที่ผู้ใช้เลือก โดยรักษางบตั้งต้นเดิม |
| F08 | P2 / design prerequisite | candidate engine หัก allocation ทุกบาทเป็น deduction | ใช้กับ ordinary investment/debt repayment/insurance premium ทั้งก้อนไม่ได้; ต้องมี tax treatment และผลต่อสินทรัพย์/หนี้ของแต่ละ action |
| F09 | P2 / local reliability | full test suite รอบแรกมี HTTP test ล้มเหลวด้วย WinError 10053 แต่ targeted rerun ผ่าน | มีความไม่สม่ำเสมอบนเครื่องนี้ ยังไม่ทราบ root cause; ไม่ควรปิด issue จากการ rerun ผ่านเพียงครั้งเดียว |

### F01 — retirement: สิทธิที่รายงานกับฐานภาษีไม่ตรงกัน

หลักฐาน: [engine.py](../../src/tax_gps/engine.py) สร้าง `AllowanceCalculation` และ
`taxable_income` ก่อนประมวลผล retirement แล้วนำ retirement ไปคำนวณ shared capacity
และสร้าง `ExistingRight(deductible_amount=amount_used)` เท่านั้น

กรณีสมมุติ: เงินเดือน 990,500, ค่าใช้จ่าย 100,000, ส่วนตัว 60,000, SSO 10,500
เพิ่ม `RetirementContribution("RMF", 100000)`:

| ผล | ไม่มี RMF | core เมื่อใส่ RMF 100,000 | ตัวอย่างหาก 100,000 มีสิทธิลดหย่อนครบ |
| --- | ---: | ---: | ---: |
| taxable income | 820,000 | 820,000 | 720,000 |
| PIT | 79,000 | 79,000 | 60,500 |
| status ที่ core ส่ง | READY | READY | ต้องผ่านกฎ RMF ก่อนรับรองผล |

ตัวเลขคอลัมน์สุดท้ายเป็นผล PIT ขั้นบันไดภายใต้สมมุติฐานว่า deduction ได้รับการยืนยัน
ไม่ใช่การตรวจสิทธิ RMF ของบุคคลจริง
RMF/PVD/ประกันบำนาญมีเงื่อนไขและ sublimit ของตนเอง จึงห้ามแก้ด้วยการหัก
`sum(retirement_contributions)` โดยไม่ตรวจประเภท
[ตารางลดหย่อนกรมสรรพากร](https://www.rd.go.th/fileadmin/download/tax_deductions_update30072567.pdf)
มีรายละเอียด RMF/PVD และเพดานกลุ่ม แต่ต้องประกอบกฎหมายที่ใช้กับปีเป้าหมาย

web adapter บล็อก retirement ที่เป็นบวกไว้แล้วใน
[demo_profile.py](../../examples/demo_profile.py) จึงไม่ได้เกิดผ่านหน้าเว็บเส้นทางนี้
อย่างไรก็ตาม public core API ยังให้ผล `READY` ซึ่ง consumer ใหม่สามารถนำไปใช้ผิดได้
ข้อเสนอระยะสั้นคือปิด unsupported profile ที่ core; ระยะถัดไปจึงรองรับแต่ละประเภท
พร้อมกฎและ fixtures ที่ตรวจโดยอิสระ

### F02 — ซื้อไปแล้วกับกำลังจะซื้อ ต้องแยกกัน

หลักฐาน: [web_demo.py](../../examples/web_demo.py) ส่ง `shared_usage` ไป
`OpportunityFacts.shared_limit_usage`; [engine.py](../../src/tax_gps/engine.py)
ไม่มี baseline deduction จากรายการนี้
[input contract](../demo/input-coverage.md) ประกาศไว้ว่าเป็น capacity fact อย่างเดียว
จึงเป็นข้อจำกัดที่ตั้งใจไว้ ไม่ใช่ bug ในสูตร capacity

แต่หากผู้ใช้กรอกยอด Thai ESG ที่ซื้อไปจริงและมีสิทธิลดหย่อน 100,000 บาท:

| ผล | เดโมปัจจุบัน | ตัวอย่างเมื่อรวม deduction เดิม 100,000 ครบ |
| --- | ---: | ---: |
| baseline PIT | 79,000 | 60,500 |
| PIT หลังซื้อเพิ่ม 100,000 | 60,500 | 45,500 |
| ประหยัดเพิ่มจากการซื้อใหม่ | 18,500 | 15,000 |

อย่าหัก `shared_usage` จาก PIT โดยตรง เพราะ capacity usage ไม่ได้พิสูจน์ eligibility,
ธุรกรรม, การเลือกใช้สิทธิ หรือวิธีทยอยสิทธิข้ามปี
ต้องมีรายการสิทธิเดิมที่ลดหย่อนได้จริง และลดวงเงินจากรายการเดียวกันโดยไม่ซ้ำ
LTF ที่สับเปลี่ยนเป็น Thai ESGX พร้อมสิทธิทยอยใช้ในปีถัดมาเป็นอีกชนิดของสิทธิเดิม
ต้องแยกจากเงินซื้อใหม่ใน pool ประจำปี
[Q&A ก.ล.ต.](https://www.sec.or.th/TH/Documents/Thai%20ESGX/QA-Thai-ESGX-010468.pdf)
อธิบายสิทธิจากการสับเปลี่ยนและการใช้วงเงินเงินใหม่

### F03 — unknown ไม่ควรกลายเป็นผลภาษีพร้อมใช้

[profile/models.py](../../src/tax_gps/profile/models.py) อนุญาต `Parent.eligible=None`
แต่ [calculation/rules.py](../../src/tax_gps/calculation/rules.py) ใช้ `if parent.eligible`
ทำให้จำนวน allowance เป็นศูนย์ ในขณะที่ [discovery](../../src/tax_gps/discovery/engine.py)
รายงาน `REQUIRES_INPUT` อย่างถูกต้อง

สคริปต์รีวิวพบ tax `READY`, PIT 79,000 พร้อม parent right `REQUIRES_INPUT`
web adapter ป้องกันกรณีนี้ด้วยการ reject unknown แล้ว แต่สถานะที่ core ไม่สอดคล้องกัน
อาจเผยผลแบบประเมินภายใต้สมมุติฐานได้ หากกำหนดสถานะและข้อสมมุติให้ชัด
ห้ามให้ consumer นำไปตีความเป็นภาษีครบทุกสิทธิ

### F04 — authoritative host ไม่ได้แปลว่า evidence ตรงข้ออ้าง

[catalog](../../src/tax_gps/opportunity/catalogs/TH-OPPORTUNITY-2026-001.json)
ระบุ source `SEC-THAI-ESG-2026` ว่าเป็น guidance เงื่อนไข Thai ESG/ESGX
และ `published_at=2025-11-18`
แต่ [URL ที่อ้าง](https://www.sec.or.th/TH/Pages/News_Detail.aspx?SECID=11881&NewsNo=167&NewsYear=2568&Lang=TH)
แสดงข่าวยอดเงินลงทุน Thai ESGX วันที่ 7 กรกฎาคม 2568 และเงื่อนไขมาตรการปี 2568
ไม่ได้ยืนยันการใช้ pool เดียวกันของเงินใหม่ในปี 2569

พบ evidence ที่ตรงกว่าใน
[Q&A ก.ล.ต. ชุดที่ 1 หน้า 1–2 / ข้อ 4](https://www.sec.or.th/TH/Documents/Thai%20ESGX/QA-LTF-to-Thai%20ESGX-010468.pdf):
มีเงื่อนไข 30%, 300,000 บาท, ถือ 5 ปี สำหรับปี 2569 และ shared pool ของเงินซื้อใหม่
ดังนั้นยังไม่มีหลักฐานจากการตรวจนี้ว่าค่าตัวเลขใน catalog ผิด แต่ source ที่แนบไม่รองรับ
ข้ออ้างทั้งหมดและ metadata ต้องแก้

ควรออกเวอร์ชันใหม่, ผูก source ใหม่กับ rule ที่ใช้, ระบุ section/page และผลการตรวจ
โดยเก็บ bundle เก่าไว้สำหรับ replay ห้ามเปลี่ยน JSON ใต้ version เดิมแล้วอ้าง replay เดิม
ส่วน SSO primary source เป็น index URL แบบ `page=4` ควรเก็บลิงก์กฎหมายตรงหรือ snapshot
แทนหน้ารายการที่ตำแหน่งเปลี่ยนได้

## Requirement ที่เสนอปรับ

รายการต่อไปนี้เป็นร่างจากการรีวิว ต้องแปลงเป็น canonical requirement ของงานถัดไป
และตรวจ policy ก่อน implementation ไม่ได้ย้อนเปลี่ยนสัญญา P1 ที่รับไว้แล้ว

| ID | ความสามารถ | เกณฑ์รับงานที่เสนอ |
| --- | --- | --- |
| R01 | ขอบเขตภาษีที่บอกได้จริง | ตรวจ income และ deduction coverage; material unsupported/unknown ทำให้ไม่เผยผลเป็น baseline ครบ; consumers อ่านสถานะเดียวกัน |
| R02 | รายการลดหย่อนที่จ่ายแล้ว | แต่ละรายการมี identity, ประเภท, ปี/วันที่จ่าย, จำนวนจ่าย, จำนวนลดหย่อนที่ยืนยัน, pool usage และ evidence; baseline/capacity ใช้รายการเดียวกันและไม่ซ้ำ |
| R03 | โปรไฟล์พนักงานที่ใช้จริง | เริ่ม PVD และสิทธิที่พบบ่อย เช่นประกันชีวิต/สุขภาพและครอบครัว; ถ้ายังไม่รองรับต้องถามและรายงานข้อจำกัด ห้ามปล่อยผ่านเพราะไม่มีช่องกรอก |
| R04 | ทั้งปีเทียบยอดจริง | แยก YTD actual, forecast ที่เหลือ, โบนัส/รายได้อื่น, วันที่ข้อมูล และ assumption; เงินเดือนทั้งปีรวมองค์ประกอบ 40(1) ที่เกี่ยวข้อง |
| R05 | ภาษีทั้งปีและยอดชำระเพิ่ม | แสดง total PIT แยก withholding/เครดิตที่รองรับ; settlement = PIT − paid/credits; ถ้า withholding ยังไม่ทราบ ยอดเพิ่ม/คืนต้อง unknown |
| R06 | ปีภาษีและ policy snapshot | เลือกเฉพาะปีที่มี pack ที่ตรวจแล้ว; ไม่คัดลอกกฎ 2026 ไปปีใหม่โดยอัตโนมัติ; retain ปีซื้อของแต่ละ investment lot และ claim schedule |
| R07 | จำนวนเงินที่ผู้ใช้ทดลอง | เลือกจำนวนภายใน budget, tax capacity และ guardrails โดยเก็บ original budget เดิม; เปรียบเทียบ 20k/50k/100k ได้พร้อมเงินที่เหลือ; ไม่อ้างว่าชุด boundary คือทุกทางเลือก |
| R08 | เปรียบเทียบด้วยเงินต้นเท่ากัน | มี NO_ACTION/รักษาเงินสด และทางเลือกที่รองรับ; เงินไม่จัดสรรยังถูกนับในทุกทางเลือก; ใช้ horizon เดียวกันและแสดงความเสี่ยงต่างกัน |
| R09 | tax effect ต่อ action | ordinary investment และโปะหนี้มี deduction = 0 เว้นแต่มีกฎตรงรองรับ; insurance/protection และรายการ cap ใช้ยอดที่ตรวจจริง ไม่หักเงินจัดสรรทั้งก้อนอัตโนมัติ |
| R10 | scenario หลังภาษีและค่าธรรมเนียม | สมมุติฐาน return/fee/tax/เงินเฟ้อเป็น input มีที่มา; unknown คง unknown; แสดง downside/base/upside และ break-even โดยไม่เรียกผลคาดการณ์ว่ารับประกัน |
| R11 | สภาพคล่องตามเวลา | แยกเงินออกวันนี้, tax cash ที่อาจเกิดภายหลัง, unlock date ของแต่ละ lot, reserve และ commitment; ไม่ใช้เงินคืนในอนาคตเป็นเงินลงทุนวันนี้ |
| R12 | แนะนำตามเงื่อนไข | ถ้าข้อมูล preference/risk/horizon ไม่พอ ให้แสดง trade-off; อธิบายทางเลือกที่ตรงเงื่อนไขผู้ใช้พร้อม assumption ไม่สร้างคะแนนรวมซ่อนน้ำหนัก |

R05 สำหรับขอบเขตพนักงานเริ่มจาก withholding 50 ทวิที่กรอกจริงได้
ยังไม่ต้องรองรับเครดิตหรือแบบอื่นทุกชนิด และควรบอกว่ากำลังเปรียบเทียบภาษีประจำปี
หรือยอด settlement บนข้อมูลคาดการณ์ ไม่ใช้คำว่า “ภาษีที่ต้องจ่าย” เหมารวมสองจำนวน

R06 ต้องแยก **ปีภาษีที่ใช้สิทธิ**, **วันที่ซื้อ/เริ่มถือ**, และ **วันที่วางแผน**
ไม่จำเป็นต้องมี multi-year projection เต็มรูปแบบเพื่อเก็บข้อมูลสามอย่างนี้ถูกต้อง

## คำว่า “คุ้มกว่า” ควรมีความหมายที่ตรวจได้

ผมเสนอให้เริ่มจากตารางผลลัพธ์ที่อธิบายได้ แล้วจึงเพิ่มคำแนะนำตามเป้าหมาย:

| มิติ | คำถามที่หน้าจอควรตอบ |
| --- | --- |
| ภาษี | เงินก้อนใหม่ลดภาษีเพิ่มเท่าไร หลังรวมสิทธิเดิมครบแล้ว? |
| เงินสด | วันนี้ต้องจ่ายเท่าไร เงินสำรองเหลือเท่าไร และอาจมี tax cash เมื่อไร? |
| สินทรัพย์และหนี้ | เงินเปลี่ยนไปอยู่ในสินทรัพย์อะไร หรือลดเงินต้นหนี้เท่าไร? |
| ความเสี่ยง | ในกรณีขาดทุนหรือจำเป็นต้องใช้เงินก่อนกำหนด มีผลอย่างไร? |
| เป้าหมาย | ระยะถือและการเข้าถึงเงินสอดคล้องกับกำหนดใช้เงินของผู้ใช้หรือไม่? |

ตัวอย่างประหยัดภาษี 18,500 จากการลงทุน 100,000 เป็นสิทธิของการซื้อครั้งนั้น
ห้ามตีความเป็นผลตอบแทน 18.5% ทุกปี เงินลงทุนยังมีมูลค่าและความเสี่ยงของตัวเอง
ส่วนเงินที่ใช้บริโภคหรือซื้อประกันมีผลต่อคุณภาพชีวิต/ความคุ้มครองที่แตกต่างกัน
จึงไม่ควรจัดอันดับทุกประเภทจาก tax_saved อย่างเดียว

สำหรับ comparison engine ในอนาคต:

- เก็บ cash flows ตามเวลา และแยก tax arithmetic ที่ยืนยันได้จากสมมุติฐานการลงทุน
- เก็บผลต่อ asset positions, debt principal และ protection แยกจาก cash outflow
- เลือกบัญชี cash flow ที่นับภาษีเพียงครั้งเดียว: ห้ามทั้งลด initial cost ด้วย tax_saved
  และบวก tax_saved เป็น cash flow ซ้ำอีกครั้ง
- เปรียบเทียบ terminal assets/cash และ outstanding debt บน horizon เดียวกัน
  หากลงทุนต่อหลังได้รับ tax cash ต้องประกาศ reinvestment assumption
- การโปะหนี้ใช้ interest/payment schedule และค่าปรับที่ตรวจจริง
  ไม่ใช้ APR × เงินต้น × จำนวนปี เป็นผลลัพธ์ทุกกรณี
- ค่าบริหารกองทุนที่รวมในสมมุติฐานผลตอบแทนสุทธิแล้วห้ามหักซ้ำ
- แสดง break-even และความไวต่อ assumption ก่อนสร้าง “ทางเลือกที่ดีที่สุด”

สถาปัตยกรรมเดิมยังใช้ต่อได้ โดยมี Scenario Comparison เป็น layer ถัดจาก tax/guardrails
และเพิ่ม action treatment ที่รองรับผลต่อสินทรัพย์และหนี้
ไม่ต้องให้ LLM ทำเลข และยังไม่จำเป็นต้องใช้ Monte Carlo หรือ live market data

## ข้อเสนอ UX จากหน้าจอและ source ที่มีอยู่

1. แสดงสรุปภาษีที่คำนวณครบแล้วหรือยัง พร้อมยอดชำระเพิ่ม/คืนเมื่อมีข้อมูล
2. ใช้ checklist ถามรายการที่มีจริง แล้วแสดงฟอร์มเฉพาะที่เกี่ยวข้อง
   เช่นถามว่ามี PVD/ประกัน/คู่สมรสก่อน ไม่ให้ค่าเริ่มต้น 0 แทนการยังไม่ได้ตรวจ
3. ก่อนทดลองลงทุน ชี้ว่ามีสิทธิเดิมที่ยังกรอกไม่ครบหรือไม่ได้ใช้หรือไม่
4. หน้าผลหลักให้เห็นสามข้อมูลก่อน: ใช้เงินเพิ่ม, ประหยัดภาษีเพิ่ม, สภาพคล่องเหลือ
   ข้อมูล hash, engine version และ acceptance status ให้เก็บในรายละเอียดผู้พัฒนา
   ส่วนความพร้อมของกฎและสมมุติฐานที่กระทบคำตอบต้องยังมองเห็นได้
5. บนมือถือใช้ comparison card หรือสลับ metric สำคัญ เพราะตาราง 11 คอลัมน์
   ต้องเลื่อนจนข้อมูลที่ใช้ตัดสินใจหลุดจากจุดอ้างอิง
6. ค่า `ALLOW` สื่อว่า “ผ่านข้อจำกัดที่ตรวจแล้ว” ไม่ใช่ suitability หรือคำแนะนำ
   เมื่อ tax benefit = 0 ให้บอกตรง ๆ ว่าไม่มีประโยชน์ภาษีเพิ่มในปีนี้

ข้อความปัจจุบันที่บอก “สิทธิที่มีอยู่ถูกนำมาคำนวณแล้ว” ควรจำกัดเป็น
“รายการที่รองรับและกรอกยืนยันแล้วรวมในผลนี้” จนกว่า coverage จะครบ

## Acceptance cases ที่ควรเพิ่มในงานถัดไป

- เงินเดือนกับ RMF/PVD ที่ยืนยันสิทธิ: ทั้ง PIT และ shared capacity เปลี่ยนถูกต้อง
  หรือถูกปิดจาก core หากประเภทนั้นยังไม่รองรับ
- ซื้อ Thai ESG ไปแล้วและซื้อเพิ่ม: baseline รวมยอดเดิมครั้งเดียว, ลด capacity ครั้งเดียว,
  และ tax saving ของยอดเพิ่มคำนวณจากฐานหลังสิทธิเดิม
- unknown parent/สิทธิเดิม/coverage: ไม่คืนสถานะ full-ready; adapter และ core สอดคล้องกัน
- withholding ต่ำกว่า/สูงกว่า PIT และ unknown: แยกยอดชำระเพิ่ม, คืน, และยังไม่ทราบ
- การแก้ forecast โบนัสเปลี่ยน annual estimate แต่ไม่เปลี่ยน actual ที่บันทึก
- ปีที่ไม่มี policy พร้อมใช้ถูกปิด; เปลี่ยน policy version ไม่ทำลาย replay เก่า
- ชนิดเงินซื้อใหม่ Thai ESGX และสิทธิจาก LTF transfer ไม่ใช้ pool ผิดหรือหักซ้ำ
- เปรียบเทียบ allocation 20k/50k/100k บน budget 100k: เงินส่วนที่ไม่ใช้ยังอยู่ในผล
- ordinary investment และโปะหนี้: ไม่ได้รับ deduction จากเงินจัดสรรอัตโนมัติ
- tax cash มาช้า, ผลตอบแทนติดลบ, ภาษีเป็นศูนย์, ขายก่อนครบเงื่อนไข:
  ไม่มีการนำ future cash มาใช้วันนี้ และเผยข้อสมมุติ/ข้อจำกัด
- reserve/หนี้/commitment: ไม่มีทางเลือกข้าม hard guardrail ที่ตั้งไว้

ควรมี golden fixtures ที่ยืนยันตัวเลขโดยอิสระจาก engine
เช่น case ครอบครัวและยอดลงทุนเดิม ไม่ใช้เพียง core output เป็น expected ของ adapter
100% coverage มีประโยชน์ด้าน regression แต่ไม่พิสูจน์ว่าขอบเขตและกฎหมายถูกต้องครบ
