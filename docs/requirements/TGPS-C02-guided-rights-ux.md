## 1. สิ่งที่ผู้ใช้กำหนดและข้อเสนอของผู้เขียน

ผู้ใช้กำหนด: “เราเน้นให้ดูเข้าใจง่าย ถ้ามีข้อมูลเยอะๆ ช่วยออกแบบหน่อยว่า
จะทำเป็นรูปแบบยังไงให้ user ใช้งานแล้วไม่งง”. ให้ทำต่อทั้ง evidence และ UX.

ข้อเสนอของผู้เขียน: ผู้ใช้พนักงานเงินเดือนที่ไม่คุ้นศัพท์ภาษีควรตอบได้ว่า
ข้อมูลครบหรือยัง → ภาษีจากข้อมูลนี้เท่าไร → สิทธิที่จ่ายแล้วถูกนับอย่างไร.
การทดลองใช้เงินเพิ่มเป็นขั้นถัดไป. ตอนร่างเป็นข้อเสนอผู้เขียน;
ผู้ใช้อนุมัติแบบหลัง handoffตาม DEC-021 ไม่ใช่การรับรองUXหรือกฎหมายของproductที่ทำเสร็จ.

คง local HTML/CSS/JS, visual language cream/forest และ automatic calculation
450ms ของ UI02. ไม่เปลี่ยน framework หรือเพิ่มบริการ/storage. เอกสารนี้เป็น
แบบสำหรับรีวิว ไม่ใช่ implementation plan และไม่เปิดใช้กฎ C02 ที่ยังไม่ผ่าน review.

## 2. รูปแบบที่เลือกเสนอ

| รูปแบบ | ข้อพิจารณา |
| --- | --- |
| ฟอร์มยาวเปิดทั้งหมด | เทียบข้อมูลได้ แต่ต้องอ่านเงื่อนไขที่อาจไม่เกี่ยวข้องจำนวนมาก |
| Wizard ทีละหน้า | เห็นทีละน้อย แต่กลับไปเทียบหลายสิทธิหรือแก้ตัวเลขลำบาก |
| **หน้าเดียว แบ่งหมวด เปิดเฉพาะรายการที่มี** | เสนอใช้: เห็นภาพรวมและกลับไปแก้ได้; ถามรายละเอียดเมื่อเกี่ยวข้อง |

ไม่ใช้ nested accordion หลายชั้นในฟอร์มหลัก. มี 3 หมวดเดิมเป็นโครง;
ภายในสิทธิที่เลือก “มี” แสดงฟิลด์ที่จำเป็นและคำอธิบายสั้นทันที.
“ดูวิธีคิด/เงื่อนไขทั้งหมด” เป็นรายละเอียดเสริม ไม่ซ่อนฟิลด์บังคับหรือเหตุผลปิดผล.

หมวด3ไม่ใช่ prerequisite ของ annual baseline หากข้อมูลนั้นไม่เกี่ยวตาม domain;
แสดง availability ของ baseline และการทดลองเงินแยกกันตามผล engine เท่านั้น.

## 4. การกรอกสิทธิทีละรายการ

แต่ละประเภทมีชื่อเต็มก่อนตัวย่อ เช่น “เงินสะสมกองทุนสำรองเลี้ยงชีพ (PVD)”.
คำถามเริ่มต้น: “ปีนี้คุณจ่ายเงินรายการนี้หรือไม่?”

| คำตอบ | สิ่งที่แสดง / ความหมาย |
| --- | --- |
| ยังไม่ได้ตอบ | ไม่มีตัวเลือกถูกเลือก; null, แสดง “ยังไม่ได้ระบุ” |
| มี | เปิดยอดจ่ายและข้อเท็จจริงจำเป็นทันที; ไม่ตั้ง eligible ให้เอง |
| ไม่มี | ยืนยันไม่มีเงินสะสม/ยอดซื้อใหม่ปีนี้; ส่ง explicit zero เฉพาะยอดนั้น ไม่ยืนยันว่าไม่มีขาย/โอน/ประวัติหรือสิทธิปีก่อน |
| ยังไม่ทราบ | คง unknown; บอกแหล่งที่ไปดูได้ โดยไม่เติมศูนย์ |

“ไม่แน่ใจ” เป็นคำตอบที่ใช้ได้ ไม่ถูกทำให้ดูเหมือนกรอกผิด.
ปุ่มตัวเลือกใช้ radio/fieldset/legend พร้อม label เต็ม; ไม่ใช้ checkbox ที่ตีความ
unchecked เป็นไม่มี. สถานะหน้าเว็บแปลจาก domain ไม่ทำ readiness engine ชุดใหม่.

ภาพร่างเมื่อเลือกว่ามี PVD:

```text
เงินสะสมกองทุนสำรองเลี้ยงชีพ (PVD)
ปีนี้คุณจ่ายเงินรายการนี้หรือไม่?
(●) มี   ( ) ไม่มี   ( ) ยังไม่ทราบ

เงินสะสมส่วนที่หักจากเงินเดือนคุณ   [          ] บาท / ปี
ดูยอดจากหนังสือรับรองหรือใบสรุปเงินสะสม · ไม่รวมเงินที่นายจ้างสมทบ

ฐานค่าจ้างที่ใช้ส่ง PVD             [          ] บาท / ปี
ฐานนี้อาจต่างจากรายได้รวม · ดูจากข้อมูลกองทุน/นายจ้าง

ข้อมูลที่ต้องยืนยันตามกฎที่อนุมัติ  [แสดงคำถามจริงทีละข้อที่เกี่ยวข้อง]
ช่องที่ยังไม่มีข้อสรุปกฎหมายไม่ถูกออกแบบให้ผ่านด้วยการกดยืนยันรวม

สถานะ: ต้องระบุฐานค่าจ้างก่อนคำนวณ
```

- ยอดจ่าย, ปีซื้อ, ประเภทสิทธิ, ข้อมูลที่จำเป็นต้องเห็น เป็นฟิลด์หลัก.
- PVD แยกเงินลูกจ้าง/นายจ้าง; อย่าบังคับกรอกยอดนายจ้างถ้าไม่มีผลต่อกฎที่รองรับ.
- RMF แยกยอดซื้อปีนี้จากยอดถือครองเก่า/รับโอน; ThaiESG แยกซื้อใหม่/ชนิดสิทธิ/
  LTF carry-forward. ใช้ถ้อยคำจากหลักฐานที่ผ่าน review ก่อน implement.
- ประวัติ/การขาย/การโอน/หลายนายจ้าง ถ้าเกี่ยวกับผู้ใช้ ต้องถามหรือให้ระบุได้;
  ไม่ซ่อนเพราะกรณียังไม่รองรับ และไม่อนุมานว่าไม่มีจากจำนวนรายการ.
- ใต้คำถามยอดจ่ายใหม่มีส่วน “กองทุนเดิมและรายการอื่นในปีนี้” แยกเสมอจาก
  การเลือกมี/ไม่มียอดจ่ายใหม่: มีขายคืน/โอน/สิทธิสืบเนื่องจากปีก่อนหรือไม่
  พร้อมมี/ไม่มี/ยังไม่ทราบ ไม่มีค่าเลือกเริ่มต้น. ถ้าเลือกมี เปิดรายละเอียดชนิด
  เหตุการณ์และประเภทสิทธิ; ไม่มีต้องเป็นการยืนยันของผู้ใช้. จึงเข้าทาง LTF
  carry-forwardหรือขายRMFได้แม้ยอดซื้อใหม่0. การยกเว้นคำถามที่ไม่เกี่ยวข้อง
  ต้องอาศัย factsและกฎ domainที่อนุมัติ ห้าม UIตัดสินเองจากการเลือกไม่มีซื้อใหม่.
- รายการเงินออมเกษียณอื่นแสดงชื่อประเภทจาก inventory ที่อนุมัติทั้งหมด;
  “ยืนยันว่าไม่มีรายการเหล่านี้” ใช้ได้เมื่อเห็นรายชื่อและขอบเขตชัดเจน ไม่ซ่อน
  unknown ประเภทอื่นไว้ใต้คำตอบเดียว. รายชื่อรอ evidence gate ของ C02.
- เปลี่ยนจาก “มี” ที่เคยกรอกยอดเป็น “ไม่มี”: แจ้งก่อนว่ากำลังนำรายการออกจาก
  การคำนวณ พร้อมยกเลิกได้; ไม่ทิ้งยอดที่ซ่อนอยู่ไปคำนวณ. พับหมวดไม่ลบข้อมูล.
  การยืนยันนี้เป็น product interaction ที่เสนอ ไม่ใช่ approval ของ agent.

## 5. ผลลัพธ์สามระดับ

### ระดับแรก: ภาพรวมที่ต้องเข้าใจได้ทันที

เมื่อ READY: ตัวเลขหลัก “ภาษีเงินได้จากข้อมูลนี้” พร้อม “บาท/ปี · ก่อนหักภาษี
ณ ที่จ่าย”; บรรทัดรอง “รวมสิทธิที่รองรับและคุณยืนยันแล้ว”. ระบุปีและขอบเขตใกล้ผล.
ไม่เรียกตัวเลขนี้ว่า “ยอดต้องจ่ายเพิ่ม/เงินคืน”. แสดงเงินได้สุทธิเป็นรายละเอียดรอง.

เมื่อไม่ READY: ใช้หัวข้อ “ยังแสดงภาษีไม่ได้” พร้อมชื่อรายการ/สิ่งที่ต้องแก้;
ไม่มี PIT, taxable, saving, candidate หรือ export ให้เห็น/ใช้จากผลเก่า.
ถ้ามีหลายเหตุผล แสดงรายการชื่อครบและจัดกลุ่ม “ต้องระบุเพิ่ม”/“ยังไม่รองรับ”;
ปุ่มเด่นพาไปจุดแก้แรกตามลำดับแบบฟอร์ม ไม่อ้างว่าแก้จุดเดียวแล้วครบ.
domain เป็นผู้ตัดสินสถานะหลักตาม precedence เดิม.

### ระดับสอง: สิทธิเดิมถูกนับอย่างไร

เปิดเมื่อผู้ใช้ต้องการดูสรุปสิทธิ; แสดงแถว/การ์ดรายการเดียวกันบน desktop/mobile:

```text
PVD                         นับในฐานภาษีแล้ว
คุณจ่าย                     … บาท
นำมาคำนวณสิทธิได้            … บาท
[ดูเหตุผลและวิธีคิด]

RMF                         ต้องระบุเพิ่ม
ยังไม่ทราบข้อมูลการซื้อที่ต้องใช้ตรวจสิทธิ
[ไปแก้ข้อมูล RMF]
```

ภาพข้างบนใช้ ellipsis ไม่ใช่ผลคำนวณจริง และไม่ได้อ้างว่าทั้งโปรไฟล์ READY.
เมื่อ nonREADY ไม่แสดงยอด claimed/excess หรือค่าสรุปที่เป็น partial tax result;
แสดงได้เฉพาะข้อมูลที่ผู้ใช้กรอกและชื่อเหตุผลที่ domain คืนมา.
เมื่อ READY จึงแสดง paid/eligible/claimed/excess ที่ reconcileจาก engine.

ป้าย “ใช้สิทธิได้” ไม่แปลว่า “ประหยัดภาษีเท่านี้”. ไม่ใส่ tax saving รายรายการ
ด้วยการนำยอดลดหย่อนคูณ marginal rate และไม่แบ่ง savingรวมให้แต่ละรายการเอง.

### ระดับสาม: วิธีคิดและแหล่งอ้างอิง

เปิด “ดูเหตุผลและวิธีคิด” แล้วเห็นยอดจ่าย → ยอดเข้าเงื่อนไข → ใช้สิทธิจริง →
ส่วนเกินพร้อมสาเหตุ. PVD แยกยกเว้นก่อนค่าใช้จ่าย/ลดหย่อนหลังค่าใช้จ่ายให้เห็น
ในส่วนนี้ แทนบังคับผู้ใช้รู้สองสูตรเพื่อกรอกยอดเดียว.

วงเงินร่วมแสดง “วงเงินตามกฎ / ใช้แล้วจากข้อมูลนี้ / คงเหลือ” เฉพาะเมื่อ engine
รองรับและ READY. แสดงร่วมครั้งเดียว ไม่สร้างเพดานแยกให้ทุกการ์ด ไม่เป็นยอดแนะนำซื้อ.
รายละเอียดกฎหมายบอกชื่อประกาศ/มาตรา/ปีที่ใช้และลิงก์แหล่งทางการ;
hash และ JSON export อยู่ในส่วนตรวจสอบขั้นสูงเดิม.

## 6. State และการแก้ข้อผิดพลาด

| สถานะ | Copy ตัวอย่าง | การตอบสนอง |
| --- | --- | --- |
| Initial / unknown | “RMF: ยังไม่ได้ระบุว่ามีหรือไม่” | เปิดไปคำถาม RMF; ไม่เริ่มที่0 |
| Missing | “PVD: ยังไม่ทราบฐานค่าจ้างที่ใช้ส่งกองทุน” | เปิดหมวด+focusฟิลด์; ไม่ echoยอดในerror |
| Unsupported | “ยังคำนวณสิทธิจากการสับเปลี่ยน LTF รายการนี้ไม่ได้” | ระบุรายการที่เป็นเหตุ; ไม่เสนอให้ลบรายการเพื่อให้คำนวณผ่าน |
| Advanced | ข้อความจาก domain ที่แปลเป็นไทยและระบุรายการ | อธิบายขอบเขต; ไม่ downgrade เป็นข้อมูลขาด |
| Eligibility false | เหตุผลเฉพาะรายการจาก domain | แยกจาก unknown; การให้สิทธิ/ปิดผลตามกฎที่อนุมัติ |
| Editing / pending | “กำลังตรวจข้อมูลล่าสุด…” | คงตำแหน่งแผง, ปิดผลเก่า+selection+export ตาม UI02 |
| Ready | “คำนวณได้ในขอบเขตที่รองรับ” | publishเฉพาะ responseล่าสุด |
| Network/server error | “คำนวณไม่สำเร็จ ลองคำนวณอีกครั้ง” | เก็บ inputในหน้านี้, ปิดผลเก่า, มี retry |

ไม่ auto-focus/เปิดหลายหมวดทุกครั้งที่พิมพ์; ทำเมื่อกดลิงก์แก้หรือ submitเท่านั้น.
ผล auto update ใช้ polite live region; ไม่อ่านทุกหลักของตัวเลขที่กำลังพิมพ์.
เหตุผลที่มีหลายรายการแสดงด้วยข้อความ+icon ไม่พึ่งสี; reduced motion ตาม UI02.
Accessible targets ไม่น้อยกว่า44 CSSpx, keyboardเข้าถึงทุกคำถาม/รายละเอียด,
320/360/390px ไม่มี horizontal scroll ของฟอร์ม. ขนาด44pxเป็น design choice.

## 7. Acceptance ของ UX draft สำหรับแผนในอนาคต

เสนอให้ทดลองกับผู้ใช้ที่ไม่ใช่ผู้เขียนระบบ ก่อนรับงาน UX:
กรอกกรณีไม่มีสิทธิ → กรอก PVDแต่ไม่รู้ฐานค่าจ้าง → พบรายการ LTFที่ยังไม่รองรับ →
ดู READY summaryและเปิดวิธีคิด. บันทึกจุดที่ติดและคำที่เข้าใจผิดตามจริง;
ยังไม่มี usability test หรือ acceptance จากผู้ใช้จริงในรอบนี้.
เพิ่มกรณีซื้อใหม่0แต่มีขาย/โอน/LTF carry-forward เพื่อจับการซ่อนเหตุปิดผล.

## 8. Dependency และขอบเขตงาน

- ต้องได้ข้อสรุป evidence/fields/claim authority จาก C02 ก่อนลงโค้ดจริง;
  draftนี้ไม่เลือกฐาน RMFหรือกฎ PVDที่ค้าง.
- ต้องรีวิวแบบนี้ และทำ requirement revision/DECสำหรับรายละเอียดที่เปลี่ยน
  ก่อน implementation. แบบนี้ไม่อนุมัติ C03/04/06หรือรับรอง UI02ย้อนหลัง.
- เดิมผลลัพธ์เปิด comparisonเป็นหลัก; ข้อเสนอให้ภาพรวมภาษีมาก่อนต้องรีวิว
  ในแผน UIที่เกี่ยวข้อง. คงทางเข้าการเปรียบเทียบเดิม ไม่ลบฟังก์ชันโดยเงียบ.
- Builderตัดสิน spacing/line breaks/DOMย่อยและชื่อภายในได้ตาม UI02;
  ห้ามแก้ความหมาย null/zero, readiness, evidence gates หรือ scopeเพื่อให้หน้าดูง่าย.
- เอกสารไม่มีการเชื่อม external service, ไม่ uploadเอกสารเงินเดือน และไม่มี storage.
